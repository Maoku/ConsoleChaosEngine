## 1. 受け取った所見と、その読み方

| # | 所見 | 本計画での扱い |
|---|---|---|
| 1 | 切り替えのギミックはできている | **中核ルールは成立している。** 触らない |

> ことごとく画面に出ないまま値だけが存在している。

### 2.1 本編はまだフェーズ 0 の足場で描いている

| `public/assets/textures/` は `.gitkeep` のみ | — |

この状態は T1-08 §7 と T1-15 §5 に「残る課題」として自分たちで記録済み。
**所見 2 は既知の宿題が表に出たもの**であって、想定外の問題ではない。

### 2.2 6 件のパズルのうち 4 件が「宣言だけで、画面に出ていない」

| パズル | 成立の根拠 | 画面に出ているか | 理由 |
|---|---|---|---|
| F-2 走査線制限 | スプライト数 | **出ている** | `applyScanlineLimit` が描画対象を実際に間引く |
| P1-1 裏側 | 投影と形状 | **出ている** | カメラと当たり判定がそのまま見える |
| F-1 色の潰れ | パレット | **出ていない** | ツタ 2 本とも `DEFAULT_COLOR` の灰色。**どの世代でも最初から同じ色** |
| S-1 半透明 | 加算合成 | **出ていない** | 描画状態は常に `blend: 'none'`（[mini_level.ts:232](src/debug/mini_level.ts)）。半透明に見える瞬間が無い |
| P2-1 影 | 動的ライト | **出ていない** | 影の描画が存在しない。光源は全世代で定数 `[0.4, 1, 0.6]`（[mini_level.ts:249](src/debug/mini_level.ts)）。`dynamicLight` を読むのはパズル定義だけ |
| P1-2 ソートの破れ | 描画順 | **出ていない** | §2.3 |

**動いていると言われた 2 件は、いずれも形状と間引きだけで成り立つもの。**
材質・陰影・重ね合わせを要する 4 件が全滅している。所見 2 の実体はこれである。

### 2.3 第3世代の「ポリゴン優先の問題」は、一度も描かれていない

| 事実 | 場所 |
|---|---|
| 三角形単位のソート `sortTrianglesByDepth` は実装・計測済みだが、`src/` のどこからも呼ばれていない | [sort.ts:184](src/render/sort.ts) / 利用は `tools/bench-sort.ts` とテストのみ |
| 実際の描画は**オブジェクト単位**で中心 Z を比較して並べている | [mini_level.ts:262](src/debug/mini_level.ts) `ordered` |
| 立方体をオブジェクト単位で並べる限り、画家のアルゴリズムは**破綻しない**（そういう配置になっていない） | — |
| 第3世代では殻が非実体になり、`GIMMICK_TYPES` のフィルタで**描画対象からも外れて消滅する** | [mini_level.ts:60, 259](src/debug/mini_level.ts) |

つまり試遊者が見ていたのは「CH 3 にすると灰色の箱が消える」であって、
描画順の破れではない。ヒント段階 4 の文面「殻の継ぎ目に入り」（[hints.ts:65](src/gameplay/hints.ts)）が
指す継ぎ目は、画面上に存在しない。

**所見 3 は正しい。現状の P1-2 は理解不能なのが当然である。**

### 2.4 テクスチャが無いため、第3世代の署名的な表現が無効化されている

| プロファイル値 | 意図 | 現状 |
|---|---|---|
| `affineTexture: true`（第3世代） | UV の遠近補正なし＝床や壁の模様が泳ぐ | シェーダは正しく実装済み（`ps1_forward.glsl`）。**貼る模様が無いので何も起きない** |
| `textureFilter` nearest / linear | 第3世代と第4世代の差 | 同上。2×2 の白では差が出ない |
| `vertexQuantize: 2`（第3世代） | 頂点が揺れる | 立方体 1 個は 8 頂点しか無く、揺れが**物体全体の平行移動**に見えて「面の波打ち」にならない |

第3世代らしさの三本柱（**テクスチャの歪み・頂点の揺れ・描画順の破れ**）が、
3 つとも画面に出ていない。第4世代との差が解像度だけになっている。

## 3. 方針

1. **中核ルール（投影・世代切替・パズルの成立条件）には手を入れない。** 所見 1 が保証している資産である
2. **プロファイルの値も変えない。** 変えるのは「値を画面に出す経路」だけ
3. **汎用のマテリアル／シェーダ体系は作らない**（GAME_PLAN §11.1.1）。
   必要なのは「世代差を出すために要る項目」だけを持つ薄い表である
4. **「消える」で表現しない。** F-2 の敵が消えるのは走査線制限そのものだから正しいが、
   殻や足場は「見え方が変わる」で表現する。消滅は理由を伝えない
5. **アセットは「作り方」ではなく「作られた物」を正本にする場合、その理由を記録に残す**（§8）。
   モデルは従来どおりスクリプトを正本とし、画像だけは成果物を正本とする

## 8. Blender MCP の使い方（再現性を壊さないための取り決め）

### 8.1 何が問題になりうるか

`asset-rules.md` §9 は、エクスポート手順を**スクリプトとして固定**することを規則にしている。

> 手順を文章だけで持つと、実際の出力とずれても気づけない。規則の正本はスクリプト側とする。

Blender MCP は**動いている Blender の状態**を操作する。対話で作った結果をそのまま
`.gltf` として確定させると、その形状を再現する手段がリポジトリから失われる。
`player.gltf` が `tools/blender_export_player.py` から何度でも再生成できるのに対し、
プロップだけが「誰も作り直せない成果物」になる。**この非対称は許容しない。**

### 8.2 役割分担

| 使うもの | 担当 |
|---|---|

## 9. 画像の発注仕様

### 9.1 全画像に共通する制約

| 項目 | 指定 | 理由 |
|---|---|---|
| 形式 | PNG（アルファは指定があるものだけ） | `asset-rules.md` §7 |
| 寸法 | 2 の冪。**上限 256×256** | 同上。内部解像度 320×240 では 256 でも過剰気味 |
| 拡大方式 | 第1〜3世代は nearest で拡大される前提 | 細い線・薄いグラデーションは破綻する |
| **陰影を焼き込まない** | 平坦に。ハイライト・落ち影・立体感の描き込みは**不可** | 陰影はシェーダが世代ごとに付ける。焼き込むと世代差が消え、第1世代の量子化でも破綻する |
| **直線・規則的な構造を持たせる** | 目地・格子・帯など | 第3世代のアフィン歪みは**直線が曲がって初めて見える**。ノイズだけの絵では何も起きない（§2.4） |
| 色数 | 8〜12 色程度に抑える | 第1世代の固定パレット（25 色・16 画素ブロック）で潰れたときに形が残る |
| **淡い色を使わない** | 低彩度・高明度の中間色は禁止 | T1-08 §4 の実測。明度が下がった瞬間に灰色へ落ち、形が消える |
| 隣り合う要素は**明度**で分ける | 色相だけの差は不可 | 同上 |
| 文字・記号・ロゴ | **入れない** | 実機名・商標の混入経路を作らない（README の方針、`npm run check:trademark`） |
| 視点 | 真正面（平行投影）。パースを付けない | テクスチャとして貼るため |

### 9.3 受け取り後にこちらで行う検査（`tools/check-textures.ts`）

| 検査 | 落ちたときの対応 |
|---|---|
| 2 の冪・上限 256・PNG・命名（小文字スネークケース） | 変換またはリテイク |
| 継ぎ目が「要」のものの上下左右の端が一致するか | リテイク |
| **第1世代の量子化を明度 1.0 / 0.7 / 0.4 で通し、色の系統が変わらないか** | 色の指定を直してリテイク（T1-08 §4 と同じ検査） |
| **第1世代の量子化後に、隣接要素の明度差が残っているか** | 同上 |
| 発注仕様との対応表が `T1-21_material.md` に記録されているか | 記録を足す |

### 9.4 再現性についての判断（記録）

モデルはスクリプトから再生成できるが、**生成画像は同じものを作り直せない**。
したがって画像は「派生物」ではなく**入力そのもの**として扱い、リポジトリに置いた PNG を正本とする。
CI は「再生成して差分ゼロ」ではなく、**§9.3 の制約検査**で品質を担保する。

この差は許容する。画像は一度決まれば変わらない静的な入力であり、
モデルのように「ゲーム側の座標定義と連動して直す」性質のものではないため。
ただし **§9.2 の発注仕様（プロンプトを含む）は必ず記録に残す**。
作り直しが必要になったとき、同じ意図から出発できる状態を保つのが再現性の代わりになる。
