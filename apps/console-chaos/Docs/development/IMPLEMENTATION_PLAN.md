## 1. 本書の位置づけとスコープ

### 1.1 本書が定めるもの

| 範囲 | 内容 | 章 |
|---|---|---|
| 開発環境 | 言語・ビルド・Lint・テスト・CI の具体的な構成 | §2 |
| コード構造 | ディレクトリ、ファイル、モジュール間の依存規則 | §3 / §4 |

### 1.2 本書が定めないもの（意図的な非対象）

- ゲームデザイン上の判断（パズルの中身、ステージ構成、難易度方針）— GAME_PLAN の管轄
- アセットの美術的方向性（配色、モデリング手法）— フェーズ 1 で別途アートガイドを作る
- 楽曲そのもののオーサリング手順 — フェーズ 1 着手時に音楽担当と決める

### 1.3 実装しないもの（Non-Goals）

GAME_PLAN §11.1.1 の「作らない」に加え、本実装計画として以下を明示的に対象外とする。**着手後にこれらが必要になったと感じた場合、まずゲーム側の要求を削れないか検討する（GAME_PLAN §15 のリスク対策）。**

| 非対象 | 代替 |
|---|---|
| シーングラフ / 汎用マテリアルシステム | 平坦な描画コマンド配列（§5.4.1） |
| 汎用 ECS ライブラリの導入 | 最小限の自作 ECS（§4.3、上限 400 行） |
| 汎用 Composer / エフェクトグラフ | 固定のフルスクリーンパス列（§5.4.5） |
| 汎用物理エンジン | AABB + スイープの自作（§5.6） |

| モバイル / タッチ入力 | 入力層の抽象化だけ先に入れる（§5.7） |
| ネットワーク機能・アカウント | `localStorage` によるローカルセーブのみ |
| レベルエディタの自作（フェーズ 2 まで） | Blender + 変換スクリプトで代替。自作エディタはフェーズ 2 で必要性を再判断 |

## 2. 開発環境とツールチェーン

### 2.1 選定

| 項目 | 選定 | 備考 |
|---|---|---|
| ランタイム | Node.js 22 LTS 以上 | CI と開発機でメジャーバージョンを揃える |
| パッケージマネージャ | npm | ロックファイル（`package-lock.json`）を必ずコミット |
| 言語 | TypeScript（`strict: true`） | GAME_PLAN §11.1 |
| ビルド | Vite | 最新安定版をロックファイルで固定。バージョン更新は独立した PR で行う |
| 3D 数学 | `gl-matrix` | 唯一の実行時依存（§2.2） |
| テスト | Vitest | 単体テスト・ゴールデンテスト |
| E2E / 描画テスト | Playwright（フェーズ 1 以降） | 実ブラウザでの WebGL2 スクリーンショット比較。CI では nightly のみ |
| Lint | ESLint + typescript-eslint | 依存方向規則を `import/no-restricted-paths` 相当で機械化（§4.2） |
| フォーマット | Prettier | 設定は既定に近づけ、議論の対象にしない |
| CI | GitHub Actions | §7.4 |

### 2.2 実行時依存の方針

**実行時依存は `gl-matrix` のみとする。** 追加したくなった場合は、以下を PR の説明に書くことを必須とする。

1. 自作した場合の見積り行数
2. その依存が持ち込む抽象のうち、本作で「取り除く対象」になるもの
3. 依存を外す場合の撤退手順

GAME_PLAN §11.1.1 の思想（汎用抽象は取り除く対象になる）は、描画基盤だけでなくプロジェクト全体に適用する。

### 2.3 npm スクリプト

| コマンド | 内容 |
|---|---|
| `npm run dev` | Vite 開発サーバ |
| `npm run build` | 本番ビルド（`dist/`） |
| `npm run test` | Vitest（単体・ゴールデン） |
| `npm run lint` | ESLint + `tsc --noEmit` |
| `npm run check:budget` | 行数バジェット検査（§5.3.3） |
| `npm run check:levels` | レベル・パズルのバリデータ（§7.3） |
| `npm run check:trademark` | 実機名・ロゴ混入チェック（§7.3、GAME_PLAN §7.1.1） |
| `npm run bench:sort` | V3 の三角形ソート計測（§8.1 T0-09） |
| `npm run verify` | 上記すべてを直列実行（CI と同一） |

### 2.4 ブランチとコミット

- `main` を常にビルド可能・プレイ可能に保つ
- 作業は `feat/<タスクID>-<短い説明>` のブランチで行い、`npm run verify` が通ってからマージ
- コミットメッセージ先頭にタスク ID を入れる（例：`T0-09: PS1 三角形ソートのベンチマークを追加`）— タスクと成果物の追跡のため

## 4. アーキテクチャ規約

### 4.1 中心となる不変条件

以下は実装全体を貫く不変条件であり、破る変更は PR で拒否する。

| # | 不変条件 | 根拠 |
|---|---|---|
| I1 | **世界の状態は常に 3D で 1 つだけ保持される。** 2D は投影であり、2D 用の状態を別に持たない | GAME_PLAN §5.2 / §11.4 |
| I2 | **ゲームロジックに世代の分岐（`if (gen === 'FC')`）を書かない。** 参照するのは `GenerationProfile` の値のみ | GAME_PLAN §4 |
| I3 | **シミュレーションは 60Hz 固定タイムステップで、描画に依存しない。** 描画が落ちてもゲームの挙動は変わらない | GAME_PLAN §8.3 |
| I4 | **シミュレーションは決定的である。** 同じ初期状態 + 同じ入力列 → 同じ結果（乱数は `core/rng.ts` 経由のみ） | 入力リプレイテスト（§7.2）の前提 |
| I5 | **世代切替はシミュレーションの真実を変えない。** 変わるのは投影・入出力の解釈だけ | ピラー P1 |

> I2 の例外は `generation/profiles.ts` と `render/pipeline.ts` の 2 ファイルのみ。ここだけが世代 ID を直接分岐してよい。ESLint のカスタムルールで機械的に検査する（§7.3）。

### 4.2 レイヤと依存方向

依存は**下向きのみ**。逆流と横断は禁止。

```
        ui/          debug/
          |             |
      gameplay/  <---  level/
          |
      generation/
       /    |    \
  render/ audio/ input/
       \    |    /
         core/
```

| レイヤ | 依存してよい | してはいけない |
|---|---|---|
| `core/` | なし（`gl-matrix` のみ） | 他のすべて |
| `render/` `audio/` `input/` | `core/`, `generation/profiles.ts` | 互いに、`gameplay/`, `ui/` |
| `generation/` | `core/` | `gameplay/`, `ui/` |
| `gameplay/` | `core/`, `generation/`, `level/` | `render/` の内部、`ui/` |
| `level/` | `core/` | `gameplay/`, `render/` |
| `ui/` | すべて | ─ |

**`gameplay/` は `render/` を直接呼ばない。** ゲーム側は `render/frame.ts` の描画コマンドを積むだけで、実際の描画方法を知らない。これにより「世代 = 投影方法の違い」という構造がコード上でも保たれる。

### 4.3 ECS の設計方針

軽量な自作 ECS（**上限 400 行**）。凝った最適化はしない。

```ts
// core/ecs/world.ts
type Entity = number;

interface ComponentStore<T> {
  add(e: Entity, value: T): void;
  get(e: Entity): T | undefined;
  remove(e: Entity): void;
  each(fn: (e: Entity, value: T) => void): void;
}
```

- コンポーネントは**プレーンなオブジェクト**。SoA 化はしない（対象エンティティ数が数百規模のため不要）
- システムは純粋な関数 `(world: World, dt: number) => void` とし、実行順を `system.ts` で明示的に配列管理する
- **世代ごとの表現はコンポーネントの付け替えで表す**（GAME_PLAN §11.1 の選定理由）。例：`Renderable2D` / `Renderable3D` ではなく、単一の `Renderable` が `GenerationProfile` で解釈を変える

### 4.4 1 ティックの進行順序

**この順序は固定する。** 順序に依存するバグ（特に FC のスプライト消滅と当たり判定）を避けるため、変更する場合は §5.4.4 の注記を読むこと。

| # | 段階 | 担当 |
|---|---|---|
| 1 | 入力サンプリング → `InputSnapshot` 生成 | `input/mapper.ts` |
| 2 | 世代切替入力の処理、トランジション状態の更新 | `generation/switcher.ts` |
| 3 | 現在の世代プロファイルによる入力制約の適用 | `input/constraints.ts` |
| 4 | ゲームプレイのシステム群（プレイヤー意図、パズルスクリプト、敵 AI） | `gameplay/` |
| 5 | 物理積分 + 衝突解決（**投影モードに従う**） | `gameplay/physics.ts` + `projection.ts` |
| 6 | トリガ判定・パズル状態更新・チェックポイント | `gameplay/` |
| 7 | オーディオイベントの発行 | `audio/engine.ts` |
| 8 | 描画コマンドバッファの構築 | `gameplay/` → `render/frame.ts` |
| 9 | 描画（FC はここでスプライト間引きを行い、結果を**次ティック用に**書き戻す） | `render/` |
| 10 | ポストプロセス（量子化 → CRT）→ 出力 | `render/postfx/` |

> **9 の書き戻しについて**：走査線スプライト制限は描画時にしか決まらないため、「消えているスプライトの当たり判定も消す」（GAME_PLAN §4.1）の反映は **1 ティック遅れる**。60fps では 16.6ms の遅延であり体感できないと判断し、この構造を採用する。パズル F-2 の設計はこの 1 ティック遅延を前提にする。

## 5. モジュール別実装仕様

以降、**実装前に固定しておくべき型とシグネチャ**を示す。ここに書かれた形を変える場合は本書を更新する。

### 5.1 core/loop.ts — 固定タイムステップ

```ts
const TICK_HZ = 60;
const TICK_MS = 1000 / TICK_HZ;
const MAX_CATCHUP_TICKS = 5;   // スパイク時の暴走を防ぐ

interface LoopCallbacks {
  tick(tickIndex: number): void;             // シミュレーション（決定的）
  render(alpha: number, dtMs: number): void; // alpha: 前ティックからの補間係数 0..1
}
```

- アキュムレータ方式。`MAX_CATCHUP_TICKS` を超える遅れは切り捨て（「時間を飛ばす」）
- `document.hidden` のときはティックを進めず、復帰時にアキュムレータをリセットする
- 描画は可変フレームレートで、位置は前ティックとの線形補間で表示する（GAME_PLAN §8.3）

### 5.2 generation/ — 世代プロファイルと切替

#### 5.2.1 profiles.ts

GAME_PLAN §4 の `GenerationProfile` をそのまま実装する。**追加の実装上の要件は以下の 2 点。**

```ts
export const GENERATION_IDS = ['FC', 'SFC', 'PS1', 'PS2'] as const;
export type GenerationId = (typeof GENERATION_IDS)[number];

// 1. 網羅性を型で保証する（Record を使い、世代追加時にコンパイルエラーを出す）
export const PROFILES: Record<GenerationId, GenerationProfile> = { /* ... */ };

// 2. 表示名は内部 ID と完全に分離する（GAME_PLAN §7.1.1）
export const DISPLAY_NAMES: Record<GenerationId, { channel: string; label: string }> = {
  FC:  { channel: 'CH 1', label: '第1世代' },
  SFC: { channel: 'CH 2', label: '第2世代' },
  PS1: { channel: 'CH 3', label: '第3世代' },
  PS2: { channel: 'CH 4', label: '第4世代' },
};
```

`profiles.ts` は**定数のみを持ち、ロジックを持たない**。この 1 ファイルを読めば 4 世代の全差分が把握できる状態を維持する。

#### 5.2.2 switcher.ts / transition.ts

```ts
type SwitchReason = 'player' | 'forced';   // forced はエリア 5 のみ（GAME_PLAN §5.4）

interface TransitionState {
  active: boolean;
  from: GenerationId;
  to: GenerationId;
  reason: SwitchReason;
  elapsedMs: number;
  durationMs: number;      // player: 350 / forced: 600
  invulnerable: true;      // 常に真。型で「無敵でない切替」を書けなくする
}
```

- 切替入力は**トランジション中も受け付ける**（キューに積み、完了後に即座に次の切替を開始）。GAME_PLAN §5.4 の「強制中もプレイヤーの切替入力は受け付ける」を一般則として実装する
- 強制切替の予告（1.5 秒前の赤点滅・アラート音）は `switcher.ts` がイベントを発行し、`ui/forced_banner.ts` と `audio/` が購読する。**演出の実装をロジックに混ぜない**
- **切替時フック**：`onBeforeSwitch` / `onAfterSwitch` を提供し、投影モードの変更に伴う位置解決（§5.5.3）をここに接続する

### 5.3 render/gl/ — WebGL2 ラッパー

#### 5.3.1 設計方針

**「薄い」を定義する：GL の概念を隠さない。** `gl.createBuffer` を `Mesh` クラスに包み替えるようなことはせず、面倒な定型（コンパイルエラーの取得、ステートの冗長設定の除去、リソースの型付け）だけを引き受ける。

### 5.4 render/ — 描画パイプライン

#### 5.4.1 frame.ts — 描画コマンドバッファ

```ts

  | { kind: 'sprite'; texture: TextureHandle; rect: Rect; worldPos: vec3; paletteIndex: number }
```

ゲーム側は世代を意識せずコマンドを積む。**同じコマンド列を 4 通りに解釈するのがレンダラの役割**であり、これが「制約は入出力にのみかける」（ピラー P1）のコード上の表現になる。

#### 5.4.2 pipeline.ts — 世代ごとの経路

| 世代 | 内部解像度 | 経路 |
|---|---|---|
| FC | 256×224 | `renderer2d` → `quantize_fc`（54 色 + 16×16 ブロック）→ CRT(RF) |
| SFC | 256×224 | `renderer2d` → `quantize_sfc`（RGB555）→ CRT(コンポジット) |
| PS1 | 320×240 | `renderer3d`（頂点量子化 + アフィン UV + 三角形ソート、深度テスト無効）→ CRT(S 端子) |
| PS2 | 640×448 | `renderer3d`（Z バッファ + バイリニア + シャドウマップ）→ CRT(コンポーネント) |

- 4 世代分の FBO は**起動時に全部作っておき**、切替時に確保しない
- 切替トランジション中は、**旧世代と新世代の両方を描画してノイズ付きでブレンドする**。これが 0.35 秒の演出になる（描画コストは一時的に約 2 倍だが、0.35 秒間のみ）

#### 5.4.3 sort.ts — PS1 の三角形単位ソート（最大のリスク箇所）

```ts

 * 三角形の重心とカメラ距離でインデックスを降順に並べ替える。

  positions: Float32Array,   // ワールド空間に変換済み、または view 空間
  indices: Uint16Array,
  cameraPos: vec3,
  out: Uint16Array,

```

実装上の要点：

- **アロケーションを毎フレーム行わない。** 作業用配列（距離キー配列、順列配列）は事前確保して使い回す
- 比較関数ベースの `Array.prototype.sort` は使わない。**距離を量子化した整数キーによる基数ソート（Radix Sort）を第一候補とする** — 比較ソートの関数呼び出しコストが支配的になるため
- 最適化の前に必ず素朴な実装で計測する。V3 の計測（§8.1 T0-09）は**素朴版と最適化版の両方を測り、生データは Git 管理外、結論は公開検証要約へ記録する**
- 予算内に収まらない場合の撤退手順は GAME_PLAN §15 のとおり：**ソート対象を「破綻を見せたいオブジェクト」に限定し、他は通常の深度テストで描く**。この切り替えはオブジェクト単位のフラグ（`DrawFlags.polygonSort`）で行えるよう、最初から設計に入れておく

#### 5.4.6 quantize/palette_fc.ts — カラークラッシュ

GAME_PLAN §11.3 の手順を実装する。**16×16 ブロックごとの使用色削減を 1 パスで完結できるかがフェーズ 0 V4 の検証対象。**

実装候補を優先順に評価する（T0-10 で決定）：

| 候補 | 手法 | 懸念 |
|---|---|---|
| A | 1 パス。フラグメントシェーダ内でブロックの 16×16 = 256 テクセルを毎フラグメント走査し、代表 3 色を決める | 256 回のフェッチ × 全画素。**負荷が非現実的な可能性が高い** |

| C | 静的な背景は CPU 側で事前計算し、動くものだけ実行時に処理 | パズル F-1（色の潰れ）は動的でなければならないため、部分的にしか使えない |

**推奨は B。** A から試して落ちるより、B を実装して A の必要性がないことを確認する順で進める。

### 5.5 gameplay/projection.ts — 投影ルール【本作の中核】

**本作で最も重要かつ最もリスクの高いモジュール。** GAME_PLAN §5.2 / §15 のとおり、ここが破綻するとコンセプトが成立しない。

#### 5.5.1 基本ルール

```ts
type ProjectionMode = 'ortho2d' | 'perspective3d';

/** AABB の重なり判定。2D モードでは Z 軸を無視する（＝ Z 方向に無限の柱として扱う） */
export function overlaps(a: AABB, b: AABB, mode: ProjectionMode): boolean {
  const xy = a.min[0] < b.max[0] && a.max[0] > b.min[0]
          && a.min[1] < b.max[1] && a.max[1] > b.min[1];
  if (mode === 'ortho2d') return xy;
  return xy && a.min[2] < b.max[2] && a.max[2] > b.min[2];
}
```

- **世界の座標は常に 3D。** 2D モードは「衝突判定で Z を見ない」だけであり、エンティティの Z 座標は保持され続ける（不変条件 I1）
- 2D モードではプレイヤーの Z 速度を 0 に固定する（XY 平面上のみ移動）
- ブロードフェーズは XY 平面上の一様グリッドで共通化し、3D モードでのみ Z のナローフェーズを追加する

#### 5.5.2 これが生む遊び（GAME_PLAN §5.2 の実装対応）

| 遊び | 実装上の帰結 |
|---|---|
| 2D 専用の橋 | Z が離れた 2 足場の XY 投影が隣接 → 2D では連続した床として `overlaps` が真を返す |
| 3D 専用の道 | 2D では手前の壁が Z 無限の柱になり通れない。3D では Z 方向に回り込める |
| 落とし穴の回避 | 手前の床が Z 無限になり、奥の穴を塞ぐ |
| 物体の重ね合わせ | 攻撃判定の AABB も同じ `overlaps` を通るため、自然に 2 つのスイッチへ同時ヒットする |

#### 5.5.3 【要決定】投影モード切替時の位置解決

**GAME_PLAN が定義していない、実装上必須のルール。** §10-A として決定を要する。以下は推奨案。

**3D → 2D（制約が緩む方向）**

Z を無視した結果、これまで衝突していなかったソリッドとめり込む場合がある。

1. プレイヤー AABB とめり込むソリッドを列挙
2. XY 平面上で最小移動量となる軸へ押し出す
3. 押し出し不能（四方が埋まっている）なら、**直前の安全座標へ復帰**する。切替中は無敵なのでダメージは発生しない（GAME_PLAN §5.1）

**2D → 3D（制約が厳しくなる方向）— こちらが本質的な問題**

2D 中にプレイヤーは「実際には Z 方向に 5m 離れた床」の上を歩けてしまう。3D に戻したとき、そのままではプレイヤーは空中に取り残されて落下し、**パズル C-2「次元の橋渡し」が成立しない。**

推奨する解決（**Z アンカー方式**）：

```ts
interface GroundAnchor {
  entity: Entity;      // 2D モード中に接地していたソリッド
  zSpan: [number, number];
}
```

1. 2D モード中、接地判定が成立するたびに接地面の Z 区間を `GroundAnchor` として記録する
2. 2D → 3D 切替時、プレイヤーの Z が `zSpan` の外にあれば、**トランジションの 0.35 秒をかけて `clamp(playerZ, zSpan)` へ補間移動**する
3. Z が `zSpan` 内、または接地していない（空中で切替）場合は Z を変更しない → 空中切替は素直に落下する

この方式の利点：

- 「2D で渡った橋の上に、3D でもちゃんと立っている」が自然に成立する
- Z の移動が 0.35 秒のトランジション中に**視覚的に見える**ため、プレイヤーが「奥行きが復活して吸い寄せられた」と理解できる。GAME_PLAN §15 の対策「切替時に Z が潰れる演出を追加する」と同じ効果を、位置解決そのものが担う
- 空中切替は Z を動かさないので、「2D の橋を渡り切る前に 3D に戻すと落ちる」という理解しやすいルールになる

**フェーズ 0 のゲート 1（投影ルールが直感的に理解できるか）は、この Z アンカー方式込みで検証する。**

#### 5.5.4 テスト（最優先で書く）

`projection.ts` は**テストファーストで実装する**。最低限、以下のケースを単体テストで固定する。

| ケース | 期待 |
|---|---|
| Z が 5m 離れた 2 つの床、XY で隣接 | 2D: 連続した床として歩ける / 3D: 間に落下する |
| Z が離れた壁が手前にある | 2D: 通過不能 / 3D: 迂回可能 |
| 2D で橋を渡り切り接地 → 3D へ切替 | プレイヤー Z が接地面の Z 区間へ収まる |
| 2D で橋の上、空中（ジャンプ中）→ 3D へ切替 | Z は変わらず落下する |
| 3D → 2D でソリッドにめり込む | XY 最小移動量で押し出される。四方が埋まっていれば安全座標へ復帰 |
| 攻撃 AABB が Z の異なる 2 スイッチと重なる | 2D: 両方ヒット / 3D: 手前のみ |

### 5.6 gameplay/physics.ts — 衝突

- AABB + スイープ（連続衝突判定）。トンネリングを防ぐ
- 解決は軸分離。X → Y → （3D のみ）Z の順で、1 ティックあたり最大 4 回の反復
- **すべての重なり判定は `projection.overlaps` を経由する。** 直接 AABB を比較するコードを書かない（ESLint で検査）
- 入力バッファ 8 フレーム / コヨーテタイム 6 フレームは全世代共通（GAME_PLAN §10.4）。物理側ではなく `input/buffer.ts` が担当する

### 5.7 input/ — 入力

```ts

  moveRaw: vec2;          // 制約適用前（デバッグ・チュートリアル表示用）
```

**制約の適用（`constraints.ts`）**

| 制約 | 実装 |
|---|---|
| FC の 4 方向化 | `move` の X/Y のうち絶対値が大きい方だけ残す。同値の場合は**直近に押された軸を優先**（GAME_PLAN §10.4） |
| FC/SFC のデジタル化 | `move` を符号のみ（-1 / 0 / 1）に落とす |
| PS1/PS2 のアナログ | キーボードでは `Shift` 併用の 2 段階速度、ゲームパッドではスティックの連続値 |

- **入力ソースの追加がゲームロジックに波及しない構造**を保つ（GAME_PLAN §10.3、モバイル対応への備え）。`source_*.ts` は `RawInput` を返すだけで、`mapper.ts` が `InputSnapshot` に変換する
- キーボードのみでクリア可能であることは**自動テストでは保証できない**ため、フェーズ 1 のプレイテストで検証する（GAME_PLAN §10.2）。ただし「キーボードで到達不能な入力値が要求されるパズル」がないことは、パズル定義の必須入力メタデータをバリデータで検査して機械的に防ぐ（§7.3）

### 5.9 level/ — レベルデータ形式

GAME_PLAN §11.4 の「レベルデータは 3D の真実を 1 つだけ持つ」を形式で保証する。

```ts
interface LevelFile {
  version: 1;
  id: string;
  sectors: Sector[];               // 手動セクタ分割（カリング単位）
  entities: LevelEntity[];
  puzzles: PuzzlePlacement[];
  checkpoints: Checkpoint[];
  spawn: { position: vec3; facing: number };
}

interface LevelEntity {
  id: string;
  type: string;
  transform: { position: vec3; rotation: quat; scale: vec3 };  // 3D の真実のみ

  model?: string;

  puzzleId: string;                 // puzzles/registry.ts のキー

  entities: string[];

```

**バリデータ（`npm run check:levels`）が検査すること：**

1. スキーマ適合と参照整合性（`entities` の ID 解決、`puzzleId` の存在）
2. `requiredGenerations` に挙げられていない世代でパズルが解けてしまわないこと（§7.3）
3. すべてのチェックポイント間が到達可能であること（グラフ接続性の静的検査）
4. FC 世代で使用するレベル要素が 8px グリッドに整列していること（GAME_PLAN §11.3）

### 5.10 ui/hints.ts — 段階的ヒント

GAME_PLAN §13.1 の 4 段階をそのまま実装する。実装上の要点のみ。

- **待ち時間の値は定数テーブルに置き、コードに埋め込まない**（GAME_PLAN §16.1-e：フェーズ 3 で調整するため）
- 段階 4（解法の直接提示）は**プレイヤーの要求時のみ**。自動提示のコードパスを持たせない
- 「同一パズルで滞在した時間」の計測は `gameplay/puzzles/registry.ts` が担当し、パズルごとの解決フラグと連動させる
- 全段階を設定で完全にオフにできること。オフ時はタイマー自体を回さない

## 6. パフォーマンス予算

ターゲット：**60fps（16.6ms/フレーム）** を、想定する最低スペック機で維持する。

### 6.1 フレーム予算の配分

| 段階 | 予算 | 備考 |
|---|---|---|
| シミュレーション（§4.4 の 1〜7） | 3.0ms | エンティティ数は数百規模を想定 |
| 描画コマンド構築（8） | 1.5ms | アロケーションを毎フレーム行わない |
| PS1 三角形ソート（9、PS1 のみ） | **2.0ms** | ★ V3 の計測対象。この値からポリゴン予算を逆算する |
| 描画呼び出し（9） | 4.0ms | ドローコール数の上限を別途定める |
| ポストプロセス（10） | 4.0ms | 量子化 + CRT。最大負荷は PS2（640×448） |
| 余裕 | 2.1ms | ブラウザ・GC のばらつき吸収 |

### 6.2 導出する予算

| 予算 | 決定時期 | 決め方 |
|---|---|---|
| **PS1 のポリゴン予算**（三角形数） | フェーズ 0 Week 2（T0-09） | ソートが 2.0ms に収まる三角形数を計測し、安全率 0.7 を掛けた値をアセット制作基準とする |
| ドローコール上限 | フェーズ 0 Week 2 | 世代ごとに計測して決める |
| テクスチャメモリ上限 | フェーズ 1 | 初回ロード時間（フェーズ 4 の課題）と併せて決める |

計測の生データは Git 管理外に**日付・機材・ブラウザとセットで**記録し、公開する結論は
[VALIDATION.md](../VALIDATION.md) に反映する。

### 6.3 計測の原則

- 最適化の前に必ず計測する。推測でコードを複雑にしない
- `debug/profiler.ts` は開発ビルドで常時オンにし、フレーム時間の内訳を画面に出す
- 「速くなったはず」のコミットには計測結果を PR に貼る

## 7. テスト戦略と CI

### 7.1 テストの階層

| 階層 | 対象 | 手段 | 実行 |
|---|---|---|---|
| 単体 | 投影ルール、入力制約、物理、パレット量子化、ソート、楽曲クロック | Vitest | 毎 PR |
| ゴールデン | 量子化結果、ソート順序 | Vitest + 固定データ | 毎 PR |
| 静的検証 | レベル・パズル・商標・行数バジェット・依存方向 | 自作スクリプト + ESLint | 毎 PR |
| リプレイ | ★ パズル 6 件の入力列を記録し、同じ結果になることを確認 | Vitest（ヘッドレス、描画なし） | 毎 PR |
| 描画 | 実ブラウザでのスクリーンショット比較 | Playwright | nightly |
| 手動 | 体験の質、プレイテスト | 人 | フェーズゲート |

### 7.2 リプレイテスト（不変条件 I4 を活かす）

シミュレーションが決定的である（§4.1 I4）ことを利用し、**入力列 + 期待される最終状態**を記録した回帰テストを作る。

```ts
// tests/unit/replay/f1_color_crush.replay.json
{ "level": "area1", "seed": 12345, "inputs": [...], "expect": { "puzzleSolved": ["F-1"], "ticks": 480 } }
```

- 描画を行わないため CI で高速に回る
- パズルのロジックを壊す変更を機械的に検出できる
- ★ の 6 パズルはフェーズ 1 で必ずリプレイを記録する

### 7.3 静的検証スクリプト

| スクリプト | 検査内容 | 失敗時 |
|---|---|---|
| `check-line-budget.ts` | `src/render/gl/` の合計行数 ≤ 1,500、ファイル別上限（§5.3.3） | CI 失敗 |
| `check-levels.ts` | レベルスキーマ、参照整合性、到達可能性、8px グリッド整列 | CI 失敗 |
| `check-levels.ts`（パズル部） | 各パズル定義の `solvableIn(profile)` を **4 世代すべてに対して評価**し、真になる集合が `requiredGenerations` と一致すること | CI 失敗 |
| `check-trademark.ts` | ソース・アセット名・UI テキストに実機名やロゴ由来の語が含まれないこと（禁止語リストを `Docs/` に置く） | CI 失敗 |
| ESLint カスタムルール | ①`gameplay/` から `render/` 内部への import 禁止 ②`profiles.ts` / `pipeline.ts` 以外での世代 ID 直接分岐の禁止 ③`projection.overlaps` を経由しない AABB 比較の禁止 | CI 失敗 |
| `gltf-preflight.ts` | アセットがローダのサブセット範囲に収まっていること | CI 失敗 |

**パズルの世代検証（3 行目）が本作で最も価値のある自動検証になる。** 「タグ付けされた世代でのみ解ける」（GAME_PLAN §11.4）を人間のレビューに任せず、パズル定義側に `solvableIn` を必ず実装させる設計にする。

```ts
// gameplay/puzzles/types.ts
interface PuzzleDefinition {
  id: string;
  requiredGenerations: GenerationId[];
  /** この世代のプロファイルで、このパズルが原理的に解けるか。CI が 4 世代すべてで評価する */
  solvableIn(profile: GenerationProfile): boolean;
  update(ctx: PuzzleContext, dt: number): void;
}
```

### 7.4 CI（GitHub Actions）

```
on: [pull_request, push to main]
jobs:
  verify:
    - npm ci
    - npm run lint          # ESLint + tsc --noEmit
    - npm run test          # Vitest
    - npm run check:budget
    - npm run check:levels
    - npm run check:trademark
    - npm run build
  nightly:                  # schedule
    - Playwright スクリーンショット比較（Chrome / Firefox / WebKit）
```

- **`main` へのマージ条件は `verify` の全通過。** 例外を作らない
- 描画テストは環境差でフレーキーになりやすいため、PR のブロッカーにはしない（nightly で検出し、担当者が確認する）
