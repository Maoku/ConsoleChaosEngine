## 1. エグゼクティブサマリ

| 項目 | 内容 |
|---|---|
| タイトル（仮） | Console Chaos |
| ジャンル | 2D/3D 横断 謎解きアクション |
| プラットフォーム | ブラウザ（PC・デスクトップ優先 / WebGL2） |
| プレイ時間 | 本編 2〜3 時間（垂直スライスは 15 分） |

**プロダクトの主張**：新しい世代ほど優れているのではない。4世代それぞれに「その世代でしか解けない謎」を必ず配置し、プレイ後にプレイヤーが各世代の長所を言語化できる状態をゴールとする。

## 2. コンセプトとデザインピラー

### 2.1 ピラー（すべての設計判断はこの3本に従う）

**P1. 制約は入出力にのみかける**
CPU・メモリ・ゲームロジックは単一のモダンなエンジンで動く。世代が切り替えても、世界の「真実」は一切変わらない。変わるのは**グラフィックス／サウンド／入力**という、プレイヤーと世界のインターフェースだけ。
→ これにより「世代＝知覚の変化」というテーマが一貫する。

**P2. 各世代に必ず「独占的な強み」がある**
どの世代にも、他の3世代では絶対に解けない謎が存在する。特にファミコン世代の強みを厚く設計する（本作の差別化ポイントであり、最も誤解されがちな部分のため）。

**P3. 切替はノーコストで、常時可能**
切替にリソースやクールダウンを設けない。プレイヤーが「今どう見えるか」を気軽に試せることが、体感的な理解の前提。ただし演出上の切替トランジション（約 0.35 秒）は挟む。

> **P3 の例外（承認済み）**：終盤エリア 5「混線区画」でのみ、環境が世代を強制的に切り替えるギミックを許容する。
> 条件は「**強制されていることがプレイヤーに一目でわかること**」。演出・UI で明示し、プレイヤーが自分の操作ミスと誤認しない状態を保つ（詳細は §5.4）。

### 2.2 プレイヤー体験の到達点

1. 「ファミコンは色が少ないから劣っている」→「色が少ないから**情報が明快**」への認識転換
2. 「3D になれば何でも見える」→「3D は**奥行きが増えた代わりに精度と明快さを失った**」への認識転換
3. 各世代の音を聞いただけで世代を判別できるようになる
4. コントローラの進化（8ボタン → アナログ → 感圧）が「できること」を規定していたと体感する

### 2.3 リファレンス（参考にする発想であり、模倣ではない）

- 次元の切替を謎にする発想：`FEZ` / `Super Paper Mario`
- レイヤー重ね合わせによる謎：`The Legend of Zelda: A Link Between Worlds`（表裏）
- ハードウェア制約の演出的再現：`Shovel Knight` / `Bloodstained: Curse of the Moon`（ただし本作は再現度を「制約」として実際にゲームプレイに効かせる点が異なる）

### 3.4 調査から導かれる「遊びに変換できる制約」

| 制約 | ゲームメカニクスへの変換 |
|---|---|
| FC: 同時 25 色 / 16×16 パレットブロック | 色の異なる 2 つの物体が同色に潰れる → 逆に「色で隠されていた同一性」が露見する |
| FC: 走査線 8スプライト制限 | 敵が多いとちらついて消える → **消えている瞬間は当たり判定も消える**（実機の見た目に忠実な仕様として） |
| FC: 三角波は音量固定 | 距離減衰しないビープ = 遠くの仕掛けの状態が音だけで常にわかる |
| FC: すべてが 8×8 グリッドにスナップ | 世界がグリッドに整列 → 隠し通路の位置が構造的に読める |
| SFC: 半透明（カラー加算/減算） | FC では不可視だった半透明の存在（水・霊・ガラス）が見える |
| SFC: 256色 | FC で同色に潰れていた 2 つのスイッチを見分けられる |
| SFC: Mode 7 | 床を俯瞰に回転させ、迷路の全体構造を読む |
| SFC: モザイク | 情報を落とすことで輪郭だけを抽出する「ぼかしフィルタ」的な謎 |
| PS1: 3D 化 | 2D では重なっていたものが分離。物体の**裏側**に回れる |
| PS1: Z バッファなし（ソート破綻） | ポリゴンの貫通が起こる場所＝**壁抜けできる場所**として設計 |
| PS1: アフィンテクスチャ歪み | ある角度から見ると床のテクスチャが割れて、下の隠し文字が読める |
| PS1: 頂点ジッター | 足場が微振動する → 精密なジャンプができない（＝ PS1 では通れない道） |
| PS1: アナログスティック | 微妙な傾きが必要な操作（そっと近づく、天秤を傾ける）が解禁される |
| PS2: 動的ライト・影 | 影の形から不可視オブジェクトの存在と形状を推理する |
| PS2: 高解像度 | FC/SFC/PS1 では潰れて読めない小さな刻印が読める |
| PS2: 感圧ボタン | 押し込み量で結果が変わる（半分開くドア、力加減が要る握力） |
| PS2: 情報過多 | ノイズ・エフェクトが多すぎて全体構造が読めない → FC に戻す動機 |

## 4. 世代を「制約セット」に落とし込む（実装仕様）

各世代は下記のパラメータセットとして実装する。ゲームロジックはこの構造体を参照するだけで、世代固有の分岐を持たない。

```ts
interface GenerationProfile {
  id: 'FC' | 'SFC' | 'PS1' | 'PS2';

  video: {
    internalWidth: number;        // FC:256 SFC:256 PS1:320 PS2:640
    internalHeight: number;       // FC:224 SFC:224 PS1:240 PS2:448
    projection: '2D' | '3D';      // FC/SFC は正射影、PS1/PS2 は透視投影
    paletteMode: 'fixed54' | 'rgb555' | 'truecolor';
    maxSimultaneousColors: number;// 25 / 256 / -1 / -1
    paletteBlockSize: number;     // FC:16 SFC:8 (px単位) / PS1,PS2: 0
    spritesPerScanline: number;   // 8 / 32 / -1 / -1
    tileSnap: number;             // FC:8 SFC:1 PS1:0 PS2:0 (px)
    alphaBlend: boolean;          // false / true(add-sub) / true / true
    depthBuffer: boolean;         // -/-/ false / true
    affineTexture: boolean;       // -/-/ true / false
    vertexQuantize: number;       // PS1 のみ 1.0（1px 格子に丸める）
    dynamicLight: boolean;        // PS2 のみ true
  };

  audio: {
    channels: number;             // 5 / 8 / 24 / 48
    synth: 'psg' | 'brr' | 'adpcm' | 'streaming';
    sampleRate: number;           // - / 32000 / 44100 / 48000
    reverb: boolean;              // false / true(echo) / true / true
    positional: boolean;          // false / false / true / true(3D)
  };

  input: {
    directional: 'dpad4' | 'dpad8' | 'analog';
    allowDiagonal: boolean;       // FC:false（本作の設計判断・§4.1 参照）
    buttons: string[];
    analogAxes: 0 | 2 | 4;
    pressureSensitive: boolean;   // PS2 のみ true
    rumble: boolean;              // PS1 以降 true
  };
}
```

### 4.1 制約に関する設計判断（実機との意図的な差分）

再現は「体感の忠実さ」を優先し、以下は意図的に実機と変える。**この差分表はレビュー時の判断根拠として維持する。**

| 項目 | 実機 | 本作 | 理由 |
|---|---|---|---|
| FC の斜め移動 | 十字キーは物理的に斜めも入る | **斜め移動を禁止（4方向）** | 「入力の粗さ」を謎に使うため。世代差が最も体感しやすい |
| FC の CPU 由来スローダウン | 処理落ちが頻発 | 再現しない（P1 による） | CPU 制約は本作の対象外 |
| PS1 のポリゴン数上限 | 約 36万/秒 | 上限は課さないが**ローポリのアセットで表現** | 制約は「見た目のルール」として与える |
| SFC ARAM 64KB | サンプル容量が厳しい | 容量制約は課さない。ただし**音源はすべて 32kHz・低ビット深度に落とす** | 音質の差だけを体感させる |
| ~~ちらつきの当たり判定~~ | ちらついても当たり判定は残る | ~~消えている間は当たり判定も消える~~ **→ 廃止（T2 の決定 2）** | 遊ぶ側の直感と噛み合わなかった（ギミックレビュー F-2）。走査線制限は**表示にだけ**効く。F-2 はちらつきを「答えを覗かせる現象」として使い直した。経緯は `Docs/PHASE2_GIMMICK_PLAN.md` §6 |

## 5. コアメカニクス

### 5.1 世代切替

- 操作：`1` `2` `3` `4` キーで直接切替、`Q`/`E` で隣接世代へ巡回（ゲームパッド接続時は L/R）
- 切替中は 0.35 秒のトランジション（CRT のチャンネル切替＝ノイズ + 走査線の乱れ + 水平同期の崩れ + 音のミュート）
- **切替中は無敵**。切替を安全な行動にすることで、試行錯誤を促す
- 切替直後に「その世代でのみ有効なもの」が画面内にある場合、微かな効果音でヒントを出す（アクセシビリティ設定でオフ可）

### 5.2 【中核発明】投影ルール — 2D世代では奥行きが潰れる

本作の謎解きの背骨。**世界は常に 3D で保持され、世代は「その世界をどう投影するか」だけを決める。**

| 世代 | 投影 | Z 軸（奥行き）の扱い |
|---|---|---|
| FC / SFC | 正射影（真横視点） | **Z が潰れる**。Z 座標が異なる物体も、画面上で重なれば「同じ場所」として衝突判定される |
| PS1 / PS2 | 透視投影（3人称） | **Z が復活**。奥行きの離れた物体は当然すれ違う |

これが生む遊び：

- **2D 専用の橋**：3D では 5m 離れた 2 つの足場が、2D 投影では隣接して見える → **FC/SFC でだけ渡れる**
- **3D 専用の道**：2D では壁に見える箇所が、3D で見ると壁の裏に回り込める通路
- **落とし穴の回避**：3D で見えている穴が、2D では手前の床に隠れて「床がある」ことになる
- **物体の重ね合わせ**：2D にすると離れた 2 つのスイッチが重なり、1 回の攻撃で同時に押せる

CORE_PLAN の「次元差: 2Dだと敵の弱点が見えないが、3Dにすると弱点攻撃可能に」は、このルールの一適用例として自然に包含される。

### 5.3 プレイヤーの基本アクション（全世代共通）

| アクション | FC | SFC | PS1 | PS2 |
|---|---|---|---|---|
| 移動 | 4方向・グリッド寄り | 8方向 | アナログ（速度可変） | アナログ（速度可変） |
| ジャンプ | 固定高さ | 固定高さ + 壁蹴り | 高さ可変（3D） | 同左 |
| 攻撃 | 正面のみ | 正面 + 溜め | 全方位（3D） | 全方位 + ロックオン |
| 微調整 | 不可 | 不可 | アナログで可能 | アナログ + 感圧 |

**重要**：能力の総量はどの世代でも等価にする。FC は「移動が粗い」代わりに「1マス単位で正確に止まれる」など、各世代で得るものと失うものを必ずペアにする。

### 5.4 強制切替（エリア 5 限定）

ピラー P3 の例外として、エリア 5「混線区画」でのみ環境側が世代を強制的に切り替える。**プレイヤーの主体性を奪う仕掛けなので、「今、外部要因で切り替えられている」ことを徹底的に可視化する。**

| 要素 | 仕様 |
|---|---|
| 予告 | 強制切替の 1.5 秒前から、CRT フレームのチャンネル表示が**赤く点滅**し、切替先の世代番号を先出しする |
| 予告音 | 通常の切替音とは明確に異なる、下降するアラート音（全世代で同一の音を使い、「システム側の音」であることを示す） |
| トランジション | 通常の 0.35 秒に対し、強制切替は **0.6 秒**かけ、水平同期の崩れを強めに出す |
| 事後表示 | 切替後 2 秒間、画面上部に「強制切替中」の帯を表示 |
| 復帰 | 強制状態が解除されたら、専用の解除音と帯の消滅で明示。以降は通常どおり自由に切り替えられる |
| 安全性 | 強制切替の瞬間もプレイヤーは無敵（§5.1 と同じ）。強制切替が直接の死因になってはならない |
| 操作の扱い | 強制中もプレイヤーの切替入力は受け付ける（一時的に戻せる）。ただし数秒後にギミック側が再び引き戻す |

**設計意図**：ここまで自由に世代を選んできたプレイヤーから選択権を奪うことで、「自分で選べることの価値」を終盤で改めて自覚させる。したがって強制切替はエリア 5 とボス戦の一部フェーズに限定し、それ以前には一切登場させない。

### 6.6 パズル設計のルール

1. **すべてのパズルは、正解世代に切り替えれば 10 秒以内に「わかる」こと。** 難しさは「どの世代を試すか」に置き、実行難度は低く保つ
2. **1 パズルにつき使う制約は 1〜2 個まで。** 3 個以上は複合パズル（C 系）としてゲーム後半に配置
3. **ヒントは常に他の世代の中にある。** 詰まったら世代を回せば必ず手掛かりが得られる状態を保つ
4. **失敗しても即死させない。** 落下は直前のチェックポイントへ 1 秒で復帰

## 7. 世界観・ストーリー・ステージ構成

### 7.1 設定

プレイヤーは、廃棄されたブラウン管テレビの内部に閉じ込められたデータ生命体。テレビには 4 つの「チャンネル」が残っており、それぞれが異なる時代の映像規格で同じ空間を映し出している。空間そのものは 1 つしかない。ただ、チャンネルによって見え方と触れ方が変わるだけ。

出口へ向かうには、4 つのチャンネルすべての「見え方」を使い分ける必要がある。

- **ストーリーは最小限に固定する（確定）**。テキストは各エリアの導入 2〜3 行のみ。カットシーンは作らない。ナラティブは「世界の見え方が変わること」自体に語らせる
- ナレーターは「テレビ本体」。世代を切り替えるたびに、その世代の音声規格で喋る（第1世代 = 短いビープのみ、第2世代 = 低品質サンプルボイス、第3世代 = 圧縮ボイス、第4世代 = クリアなボイス）。**声の質そのものが技術史の説明になる**

### 7.1.1 名称の扱い（商標配慮・確定）

**作中・UI・アセットに実在するハードウェアの名称、ロゴ、筐体・コントローラの固有形状、起動音は一切使用しない。**

| 用途 | 表記 |
|---|---|
| 作中・UI 表示 | 「CH 1」〜「CH 4」／「第1世代」〜「第4世代」 |
| ソースコード・設計文書の内部 ID | `FC` / `SFC` / `PS1` / `PS2`（本書での表記もこれに準じる） |
| README・ストアページ | 実機名は「参考にした技術世代の説明」としてのみ記述可 |

**README に必ず明記する事項：**

1. 本作は特定のゲーム機のエミュレータではなく、ROM・BIOS・実機アセットを一切使用・同梱しないこと
2. 各世代の表現は、公開されている技術仕様を参考にした**独自実装による様式的な再現**であること
3. 言及する製品名・会社名は各社の商標であり、本作は権利者と一切関係がないこと
4. 実機の挙動と意図的に異なる箇所があること（§4.1 の差分表への参照）

コントローラを画面に表示する場合も、実機の形状を模さない抽象的な図案（ボタン数と入力軸だけを示す記号）を用いる。

> チェック方法：フェーズ 1 完了時にアセットとテキストを全走査し、実機名・ロゴ・固有形状の混入がないことを確認する。

### 7.2 ステージ構成

| エリア | 主題 | 導入する制約 | 想定 |
|---|---|---|---|
| 0. 走査線の間（チュートリアル） | 切替そのもの | 4 世代の基本的な見た目の差 | 5分 |
| 1. パレットの回廊 | **色** | FC の色数制約 / SFC の 256色（F-1, S-3） | 20分 |
| 2. 次元の坑道 | **次元** | 2D 投影と 3D の往復（P1-1, C-2） | 25分 |
| 3. 反響の広間 | **音** | 各世代の音源特性（F-4, C-4） | 20分 |
| 4. 制御の塔 | **入力** | 4方向 / アナログ / 感圧（P2-3, P1-4） | 25分 |
| 5. 混線区画 | **総合** | 複合パズル C 系 + **強制切替**（§5.4。本作で唯一プレイヤーから切替の主導権を奪うエリア） | 30分 |
| 6. 終端（ボス） | 総合 | 4 世代を高速で往復するボス戦 | 15分 |

### 7.3 ボス設計（一例）

ボスは 4 つの「層」を持ち、各層は 1 つの世代でしか攻撃できない。

- FC 層：ちらつきで一瞬だけ露出する核（F-2 の応用）
- SFC 層：半透明で、SFC でしか見えないシールド
- PS1 層：背面にしか弱点がない（回り込みが必要）
- PS2 層：影を読んで本体の位置を特定する

**全部の世代を使わないと勝てない**というゲーム全体の主張を、戦闘という形で締めくくる。

## 8. 表示の統一 — CRT レイヤー仕様

CORE_PLAN の「表示装置としてブラウン管テレビに表示されている設定とし、見た目のサイズを揃える」を以下で実装する。

### 8.1 パイプライン

```
[世代別レンダリング]
  FC   → 256×224 の RGBA バッファ（パレット量子化 + タイルスナップ）
  SFC  → 256×224 の RGBA バッファ（RGB555 量子化）
  PS1  → 320×240 の RGBA バッファ（頂点量子化 + アフィンUV + ソート描画）
  PS2  → 640×448 の RGBA バッファ（Zバッファ + バイリニア + ライティング）
        ↓
[共通スケーリング] すべて 4:3 のセーフエリアに整数比＋アスペクト補正でフィット
        ↓
[CRT ポストプロセス] 走査線 / シャドウマスク / NTSC にじみ（コンポジット風の色差） /
                     バレル歪み / ブルーム / ビネット / 微小なノイズと揺れ
        ↓
[TV フレーム] 木目調の筐体、画面周囲の反射、チャンネル表示
        ↓
[画面出力]
```

### 8.2 世代を CRT 側でも表現する（重要）

同じ CRT でも、世代によって「接続方式」が違ったという史実を演出に使う。**これがサイズを揃えたうえでの差別化になる。**

| 世代 | 想定接続 | ポストプロセス設定 |
|---|---|---|
| FC | RF（アンテナ端子） | 色にじみ最大、輝度ノイズ、色ずれ、走査線くっきり |
| SFC | コンポジット | にじみ中、ドットクロスあり |
| PS1 | S端子 | にじみ小、色分離良好 |
| PS2 | コンポーネント / D端子 | ほぼクリア、インターレースのちらつきを再現 |

### 8.3 パフォーマンス方針

- ターゲット：60fps（内部シミュレーションは 60Hz 固定タイムステップ、描画は可変）
- 内部解像度が最大でも 640×448 のため、GPU 負荷は主にポストプロセスに集中する
- 低スペック向けに CRT エフェクトの段階設定（Off / Light / Full）を用意

## 9. サウンド設計

### 9.1 実装方針

すべて Web Audio API 上で、**同一の楽曲データ（内部フォーマット：ノート＋パラメータ）を 4 通りに再生する。**

| 世代 | 実装 |
|---|---|
| FC | `PeriodicWave` による矩形波（デューティ 12.5/25/50/75%）×2、三角波×1、`AudioBufferSourceNode` によるノイズ×1、低ビットレート PCM ×1。**同時発音 5 に達したら古い音を切る**（実機の発音数制約を再現） |
| SFC | 事前に用意したサンプル群を 32kHz / 疑似 BRR（4bit ADPCM 相当の劣化を焼き込み）で再生。ADSR エンベロープ、`ConvolverNode` によるエコー。同時発音 8 |
| PS1 | 44.1kHz サンプル + リバーブ。BGM はストリーミング（1 本のオーディオファイル）。同時発音 24 |
| PS2 | 48kHz、`PannerNode` による 3D 定位、環境音の多層レイヤー、同時発音 48 |

### 9.2 世代切替時の音の連続性

BGM は**同じ曲の同じ小節位置**を保ったまま音源だけが切り替わる。これにより「同じ音楽が、時代の技術で書き換わる」体験が生まれる。切替の 0.35 秒はホワイトノイズでマスクする。

→ 楽曲は「4 世代分の編曲」を持つ 1 曲としてオーサリングする（作曲コスト増。§15 リスク参照）。

### 9.3 効果音の役割

FC の効果音は**種類が少ないため、1 つ 1 つが明確な意味を持つ**。この特性を F-4 のような謎に活かす。逆に PS2 では環境音が豊かで、意味のある音がその中に埋もれる（＝情報過多の体感）。

## 10. 入力設計

### 10.1 キーボードマッピング（ゲームパッド未接続時）

| 機能 | キー | FC | SFC | PS1 | PS2 |
|---|---|---|---|---|---|
| 移動 | WASD / 方向キー | 4方向のみ | 8方向 | 8方向（速度は一定） | 同左 |
| アナログ微調整 | `Shift` 押しながら移動 | ✗ | ✗ | ✓ | ✓ |
| ジャンプ | `Space` | ✓ | ✓ | ✓ | ✓ |
| 攻撃 / アクション | `J` | ✓ | ✓ | ✓ | ✓ |
| サブアクション | `K` | ✗ | ✓ | ✓ | ✓ |
| 感圧（押し込み量） | `L` の長押し時間で代替 | ✗ | ✗ | ✗ | ✓ |
| 世代切替 | `1`〜`4` / `Q` `E` | ─ | ─ | ─ | ─ |

**設計上の課題**：キーボードには感圧もアナログもない。以下で代替する。

- アナログ入力 → `Shift` 併用による「歩き」モード（速度 2 段階）＋マウス移動量
- 感圧 → ボタンの押下時間を 0〜1 に正規化（0.5 秒でフルスケール）。UI にゲージを表示

### 10.2 ゲームパッド対応（オプション・確定）

**ゲームパッドは必須にしない。キーボードのみで最後までクリアできることを保証する。**

Gamepad API で対応し、接続されている場合は**アナログ・感圧・振動を本来の形で使う**（PS1 以降でのみ有効化）。振動は PS1/PS2 の世代でのみ発生し、これ自体が世代差の体感になる。

| 項目 | キーボード | ゲームパッド |
|---|---|---|
| アナログ移動 | `Shift` 併用の 2 段階速度で代替 | スティックによる連続値 |
| 感圧入力 | 押下時間を 0〜1 に正規化（0.5 秒でフル） | アナログトリガー／感圧ボタンの実値 |
| 振動 | なし（画面の微振動で代替表現） | あり |
| クリア可能性 | **保証する** | 保証する |

**検証項目**：フェーズ 1 のプレイテストで、キーボードのみのプレイヤーとゲームパッドのプレイヤーで、各パズルのクリア時間に有意な差が出ないことを確認する。差が出た場合はキーボード側の代替手段を作り直す。

### 10.3 モバイル対応（初期スコープ外・確定）

初期リリースのスコープからは外す。ただし将来的な追加を見据え、**横持ち＋バーチャルパッド**を想定した設計上の備えだけは今から入れておく。

| 項目 | 方針 |
|---|---|
| 想定形態 | 横持ち。画面左に方向入力、右にアクションボタン、**世代切替は画面上部に 4 つのチャンネルタブ**として常時表示 |
| 今やっておくこと | 入力層を抽象化し（`input/mapper.ts`）、入力ソースの追加がゲームロジックに波及しない構造を保つ。UI のセーフエリアを最初から意識してレイアウトする |
| 今やらないこと | タッチ実装、レスポンシブレイアウト、モバイル向けの描画負荷最適化 |
| 判断の見送り | 感圧入力（PS2）のタッチ代替は未解決。長押し時間か、`Touch.force`（対応端末のみ）かは、モバイル対応に着手する時点で決める |

**注意**：`Shift` 併用のアナログ代替（§10.1）はタッチに持ち込めない。モバイル版ではバーチャルスティックの傾き量をそのまま使う想定とし、キーボード用の代替手段とは別系統として設計する。

### 10.4 入力制約の「気持ちよさ」を守る

FC の 4 方向移動は不便だが、不快であってはならない。

- 入力バッファ（8フレーム）とコヨーテタイム（6フレーム）は全世代で適用
- FC ではキャラクターの移動がグリッドに吸着し、「狙った場所にぴたりと止まれる」快感を与える
- FC で斜めに入力された場合、直近に押された軸を優先（意図しない停止を防ぐ）

## 11. 技術アーキテクチャ

### 11.1 スタック

| レイヤー | 選定 | 理由 |
|---|---|---|
| 言語 | TypeScript（strict） | 型で `GenerationProfile` の網羅性を保証する |
| ビルド | Vite | 高速な HMR、静的サイトとして配布可能 |
| 描画 | **WebGL2 直叩き**（薄い自作ラッパー） | 意図的に壊れた描画（ポリゴン単位ソート、アフィン UV、パレット量子化）がコアであり、汎用エンジンの抽象は取り除く対象になる（§11.1.1） |
| 3D 数学 | `gl-matrix` | ここは自作しない |
| モデル読込 | 自作の glTF 2.0 サブセットローダ | 使う機能が限られるため、汎用ローダを抱える必要がない（§11.1.1 のスコープ表） |
| ポストプロセス | 自作のフルスクリーンパス列 | パレット量子化・CRT を固定のパス列で実装。汎用 Composer は作らない |
| 音 | Web Audio API 直叩き | 世代ごとの音源合成を細かく制御する必要がある |
| 状態管理 | 自作 ECS（軽量） | エンティティに世代ごとの表現コンポーネントを付け替える構造と相性が良い |
| 物理 | 自作（AABB + スイープ） | 「2D では Z が潰れる」という独自ルールが必要なため既製品が使えない |
| テスト | Vitest | パズルのロジックとコリジョンを単体テスト |

#### 11.1.1 描画基盤の方針（確定：WebGL2 直叩き）

**汎用 3D エンジン（Three.js 等）は採用しない。薄い自作ラッパー越しに WebGL2 を直接叩く。**

##### 採用理由

本作の描画は「正しく速く描く」ことを目的としない。**意図的に壊れた描画**こそが本体であり、汎用エンジンが提供する抽象（マテリアル体系、自動ソート、自動ステート管理）は、そのほとんどが取り除きたい対象になる。

| 要件 | 汎用エンジンだと | 直叩きなら |
|---|---|---|
| PS1 の**ポリゴン単位ソート**（Z バッファなし） | メッシュ単位の描画順制御しかできず、実機の破綻を再現できない。メッシュ分割による回避はオーサリングを歪める | 描画前にインデックスバッファを重心距離で並べ替えるだけ。**実機と同じ粒度で再現できる** |
| PS1 の**アフィンテクスチャ** | マテリアル体系を貫通してシェーダを書き換える必要がある | 自前のシェーダなので最初からそう書く |
| PS1 の**頂点量子化** | シェーダ注入（`onBeforeCompile` 等）に依存し、ライブラリ更新で壊れる | 頂点シェーダに 1 行足すだけ |
| FC の**16×16 カラークラッシュ** | ポストプロセス基盤に乗せられるが、そのために基盤全体を抱える必要がある | 自前の FBO とフルスクリーンパスで完結 |
| **4 世代のパイプライン切替** | 2 系統のレンダラを保持することになり、状態管理が二重化する | 単一のコマンドバッファに対し、世代ごとにステートとシェーダを差し替える |

加えて、本作の 3D は**PS1 相当のローポリ + PS2 相当の前方レンダリング**までで、PBR・IBL・複雑な影・インスタンシングといった汎用エンジンの主要機能をほとんど使わない。抱えるコストに対して得られるものが少ない。

##### 自作する範囲（スコープを先に固定する）

「必要になったら足す」で肥大化させないため、**作るものと作らないものを最初に線引きする。**

| 作る | 内容 |
|---|---|
| GL ラッパー | シェーダのコンパイル/リンク、VAO・VBO・UBO、テクスチャ、FBO、ステートキャッシュ。**約 1,500 行を上限とする** |
| シーン表現 | 平坦な描画コマンド配列（ツリー構造・シーングラフは作らない） |
| モデルローダ | glTF 2.0 の**サブセット**のみ。メッシュ、マテリアルの baseColorTexture、スキニング、ボーンアニメーション。それ以外は読み飛ばす |
| ポストプロセス | フルスクリーンパスのチェーン（パレット量子化、CRT）。汎用的な Composer は作らず、固定のパス列で足りる |
| 数学 | `gl-matrix` を使用。ここは自作しない |

| 作らない | 理由 |
|---|---|
| シーングラフ / 汎用マテリアルシステム | 4 世代分のシェーダは手書きの固定数で足りる |
| PBR・IBL・SSAO・ディファードレンダリング | どの世代でも使わない |
| 汎用のカリング機構 | レベルは手動でセクタ分割し、セクタ単位で出し分ける |
| WebGPU 対応 | 初期スコープ外。ただし GL ラッパーの API は将来差し替えられる形にしておく |

##### フェーズ 0 での検証項目

判定ではなく、**方式が確定したうえでの実装確認**として行う。

| # | 項目 | 確認したいこと |
|---|---|---|
| V1 | PS1 頂点量子化 | `floor(pos.xy / pos.w * res) / res * pos.w` で実機らしい揺れが出るか。量子化の粒度を調整可能にする |
| V2 | PS1 アフィンテクスチャ | UV を `w` で割らない補間で、実機らしい歪みが出るか。ポリゴン分割数との兼ね合いを詰める |
| V3 | PS1 ポリゴン単位ソート | 三角形の重心距離でインデックスを並べ替え、**60fps を維持できる三角形数の上限**を計測する（ソートは CPU 側 O(n log n)） |
| V4 | FC パレット量子化 + 16×16 カラークラッシュ | 1 パスで実現できるか。ブロックごとの使用色削減をどう実装するか（後述の候補あり） |
| V5 | FC 走査線スプライト制限 | CPU 側の可視性制御。描画基盤に依存しない |
| V6 | CRT ポストプロセス | 4 世代分のプリセットを 1 つのシェーダのパラメータ違いで表現できるか |
| V7 | 世代切替時のパイプライン差し替え | シェーダを事前に全コンパイルしておき、切替時にコンパイルが走らないこと。60fps 維持を計測 |

**V3 と V4 が主な計測対象。** V3 はソートの CPU コスト、V4 はブロック単位の色削減をシェーダで完結できるか（できなければコンピュート的な多パス、または CPU 側の事前計算に切り替える）。

### 11.3 レンダリングの要点

**FC のパレット量子化**
1. シーンをフルカラーでレンダリング
2. フラグメントシェーダで 54 色マスターパレットへ最近傍量子化
3. 16×16 ピクセルブロックごとに使用色を 3 色（+背景色）に削減。**ここでカラークラッシュが自然に発生する**
4. 8×8 グリッドへのスナップは、そもそもレベルデータをグリッド設計にすることで満たす

**FC のスプライトちらつき**
走査線ごとにスプライト数をカウントし、9 個目以降を破棄。破棄されたスプライトの当たり判定も同フレームで無効化する（§4.1 の意図的差分）。

**PS1 の描画**（§11.1.1 V1〜V3）
- 頂点シェーダで、クリップ空間座標をスクリーン解像度の 1px 格子に丸める（`floor(pos * res) / res`）
- テクスチャ座標は `noperspective` 相当にする（`w` で割らない）＝ GLSL では varying を手動で線形補間するか、頂点の `w` を 1 に固定
- 深度テストを無効化し、**三角形単位**で重心距離ソートして描画する。CPU 側で毎フレーム、インデックスバッファを並べ替えて再アップロードする
  - 実機と同じ粒度なので、ソート破綻（貫通・ちらつき・描画順の入れ替わり）が**自然に発生する**。P1-2「ソートの破れ」はこの自然発生を利用し、意図した場所で確実に起きるようジオメトリを配置して設計する
  - 並べ替えの CPU コストが唯一の懸念。フェーズ 0 の V3 で 60fps を維持できる三角形数の上限を計測し、その値を PS1 世代のアセット制作基準（ポリゴン予算）として文書化する

**PS2 の描画**
標準的な前方レンダリング + シャドウマッピング + バイリニア。ここは「普通に作る」ことが正解。

### 11.4 レベルデータの権威性

**レベルデータは 3D の真実を 1 つだけ持つ。** 2D 表現は投影であり、別データを持たない。これを守らないと 4 世代分のレベルを作ることになり破綻する。

- レベルは Blender または自作エディタでオーサリング → glTF ライクな独自 JSON に変換
- パズル要素は「必要世代」タグを持つエンティティとして配置
- **バリデータを CI で走らせる**：各パズルが「タグ付けされた世代でのみ解ける」ことを自動検証する

## 12. アセットパイプライン

| 種別 | 制作 | 変換 |
|---|---|---|
| 3D モデル | Blender でローポリ制作（PS1 相当を基準とする） | PS2 用にスムーズシェーディング / FC・SFC 用は正射影ビューをリアルタイム量子化（焼き込みはしない） |
| テクスチャ | 元は 256×256 で制作 | PS2:256、PS1:64（ニアレスト）、SFC/FC:量子化してタイル化 |
| 楽曲 | DAW で 1 曲 → 4 編曲 | FC:合成パラメータ、SFC:32kHz サンプル、PS1/PS2:ストリーミング |
| 効果音 | 同上 | 世代ごとに 4 バリエーション |
| UI | ビットマップフォント 3 種（8px / 8px高精細 / TrueType） | 世代に応じて切替 |

### 12.1 プレイヤーキャラクター（確定：3D モデル）

**プレイヤーキャラクターは 3D モデルを唯一の権威データとし、FC/SFC では正射影ビューをリアルタイム量子化して表示する。手描きのドット絵は用意しない。**

| 判断 | 内容 |
|---|---|
| 採用理由 | §11.4 の「権威データは 1 つ」という原則を、キャラクターにも一貫して適用できる。アニメーションが 1 セットで済み、4 世代分のドット絵（各方向・各アクション）の作成と同期維持が不要になる |
| 引き換えに失うもの | 手描きドット絵ならではの誇張表現・愛嬌。量子化結果が「3D を無理やりドットにしたもの」に見えるリスク |
| 対策 | **モデルを最初からローポリ・大きめのシルエットで設計する**。量子化後に潰れないよう、頭身を低く、パーツのコントラストを強くする。テクスチャは面ごとのフラットカラーを基本とし、グラデーションを避ける |
| 検証 | フェーズ 1 のプレイテストで、FC 表示時のキャラクターが「読みやすいか」「魅力があるか」を必ず確認する。読みにくい場合はモデル側（シルエット・配色）を直す。**ドット絵の手描きに戻す選択肢は取らない** |

アニメーションはボーンアニメーションで作成し、FC 表示時のみ**再生をコマ落とし**（6fps 程度に間引き）して、当時のアニメーション枚数の少なさを表現する。

### 12.2 アセット量の削減方針

FC/SFC のグラフィックスは、**すべて 3D モデルからのリアルタイム量子化で生成する**。手描きのドット絵アセットは本作に存在しない。これにより、世代を追加・調整してもアセットの作り直しが発生しない構造を保つ。

## 13. UI / UX とアクセシビリティ

- **常時表示**：現在の世代を示すインジケータ（チャンネル番号 + 世代名）。これは CRT フレームの外側に置き、ゲーム画面の再現性を汚さない
- **世代ヒント**：任意で ON にできる「この場所には他の世代で見えるものがある」の微弱な表示
- **色覚特性への配慮**：色を識別するパズル（S-3 など）には、必ず形または音による代替手掛かりを併設する
- **光過敏への配慮**：CRT のちらつき・走査線・世代切替ノイズをすべて減衰できる設定。F-2 のちらつきは**ヒントであって当たり判定ではない**ので（T2-02）、明滅を弱めても解ける（灯の位置は幕の裂け目から読めれば足りる）
- **キーコンフィグ**：全キー再割り当て可
- **オートセーブ**：エリア単位 + パズル解決ごと。`localStorage` に保存

### 13.1 難易度とヒント（確定：難易度選択は設けない）

**難易度選択肢（イージー／ノーマル／ハード）は用意しない。** 理由は 2 つ。

1. 本作の難しさは実行難度ではなく「どの世代を試すか」という**気づき**にある。数値を弄って易しくすることに意味がない
2. 難易度を下げたプレイヤーが、ピラー P2（各世代の魅力を体感させる）の核心部分をスキップしてしまう恐れがある

代わりに**段階的ヒントシステム**を用意し、詰まったプレイヤーだけが自分のペースで引き出せるようにする。

| 段階 | 内容 | 提示条件 |
|---|---|---|
| 0 | なし | 通常 |
| 1 | 「この場所には、別の世代でしか見えないものがある」 | 同一パズルで 3 分経過、またはプレイヤーがヒントを要求 |
| 2 | 対象の世代を示す（例：「CH 1 で見てみよう」） | 段階 1 から 2 分経過、またはヒント要求 |
| 3 | 使う制約を明示（例：「色が同じものは、同じものとして扱われる」） | 段階 2 から 2 分経過、またはヒント要求 |
| 4 | 解法の直接提示 | ヒント要求のみ（自動では出さない） |

- **段階 4 以外は自動でも出るが、すべて設定で完全にオフにできる**（自力で解きたいプレイヤーのため）
- ヒントを見てもペナルティはなく、その旨を UI で明示する
- ヒントのテキストは、どの段階でも「答え」ではなく「見る場所」を示す方向で書く

## 15. リスクと対策

| リスク | 影響 | 対策 |
|---|---|---|
| **投影ルール（§5.2）がプレイヤーに伝わらない** | 致命的。ゲームが成立しない | フェーズ 0 で最優先検証。伝わらない場合は、切替時に「Z が潰れる」アニメーション演出を追加する |
| **アセット制作量が 4 倍になる** | スケジュール破綻 | 3D 権威データ + リアルタイム量子化（§12）を徹底。手描きは最小限に限定 |
| **楽曲が 4 編曲必要でコスト過大** | スケジュール圧迫 | 楽曲数を絞る（全 5 曲程度）。編曲は同一のノートデータからの音源差し替えを基本とし、FC のみ手動で発音数調整 |
| **ファミコン世代が「劣った世代」として体感されてしまう** | ピラー P2 の失敗＝作品の主張の崩壊 | FC 専用パズルを他世代より 1〜2 件多く配置。フェーズ 1 のゲートで必ず検証 |
| **自作 GL ラッパーが肥大し、エンジン開発がゲーム開発を侵食する** | スケジュール破綻。直叩き方針の最大リスク | §11.1.1 で「作る／作らない」を先に固定。1,500 行の上限をフェーズ 0 のゲートで機械的にチェックする。**機能が足りないと感じたら、まずゲーム側の要求を削れないか検討する** |
| **PS1 の三角形単位ソートが CPU を食い潰し 60fps を割る** | PS1 世代の表現が成立しない | フェーズ 0 の V3 で上限を計測し、**ポリゴン予算としてアセット制作基準に落とす**。予算内に収まらない場合は、ソート対象を「破綻を見せたいオブジェクトのみ」に限定し、他は通常の深度テストで描く |
| **FC の 16×16 カラークラッシュがシェーダ 1 パスで実現できない** | 描画コスト増、または実装の複雑化 | フェーズ 0 の V4 で確認。不可なら多パス化、または静的な部分を CPU 側で事前計算する |
| **glTF ローダのサブセットが後から足りなくなる** | 手戻り | 対応範囲をローダの README に明記し、**アセット側をその範囲に合わせて作る**（Blender のエクスポート設定をテンプレート化）。ローダを拡張する前にアセットを直す |
| **プレイヤーの 3D モデルが FC 量子化で潰れて魅力を失う** | 主人公の印象が悪化 | モデルをローポリ・低頭身・高コントラストで設計（§12.1）。フェーズ 1 のゲート 2 で検証し、モデル側を直す（ドット絵への差し戻しはしない） |
| **強制切替（エリア 5）がプレイヤーの不満を招く** | 終盤の体験悪化 | §5.4 の可視化を徹底し、無敵・入力受付を保証する。フェーズ 3 のプレイテストで「理不尽さ」を訴える声が出たら、強制の頻度を下げる |
| **ブラウザ間の WebGL2 / Web Audio 差異** | 一部環境で動作不良 | フェーズ 0 の段階から Safari を含めて確認する。Safari の Web Audio は特に要注意 |
| **世代切替の多用でプレイヤーが混乱・疲弊** | 体験の質低下 | 切替を無コスト・常時可能にし（P3）、詰まっても損しない設計を守る。1 パズルで使う世代は最大 2 つ（複合パズルを除く） |
| **CRT ポストプロセスが低スペック機で重い** | 対象環境の縮小 | 3 段階の品質設定を早期に実装 |
| **スコープの肥大** | 未完成リスク | エリア単位で切れる構造にする。最悪エリア 5 を削ってもゲームは成立する |
