# T1-20 外部プレイテスト（5〜8 名）— 実施キット

| 項目 | 値 |
|---|---|
| 日付 | 2026-08-02（キット作成。**実施は未了**） |
| 対象 | エリア 1「パレットの回廊」（想定 15 分） |
| 遊ぶ | `npm run playtest` → 表示された URL（`?tester=01` を付ける） |
| 記録 | 自動（`src/debug/playtest_log.ts`）。終了画面の「記録を保存」で JSON |
| 集計 | `npm run playtest:report -- <JSON…>` |
| 判定するもの | ゲート G1-1 / G1-2 / G1-3（GAME_PLAN §14、IMPLEMENTATION_PLAN §8.2） |

> **このタスクは人が要る。** 5〜8 名の外部プレイヤーに触ってもらう部分は実施できていない。
> ここにあるのは、実施のための手順・記録の取り方・集計の仕方である。
> 実施後、結果を本ファイルの §7 に追記してゲート判定を行う。

## 0. 準備（進行役）

```bash
npm run playtest
```

ビルドしてプレビューサーバを立てる（`--host` つきなので、同じネットワークの
別の PC からも開ける。試遊者の使い慣れた機械で遊んでもらう場合はこちら）。

試遊者ごとに **`?tester=01`** のように通し番号を付けた URL を開く。
番号は記録ファイルに入る。**氏名は入れない**（記録に個人が残らないようにする）。

| 例 | 用途 |
|---|---|
| `http://localhost:4173/?tester=01` | 1 人目 |
| `http://192.168.x.x:4173/?tester=02` | 別の PC から遊ぶ 2 人目 |
| `…/?tester=03&playtest=0` | 開始画面を出さない（開発中の確認用） |

画面に出るのは**開始画面 →（プレイ）→ 終了画面**の 3 つだけ。

| 場面 | 何が起きるか |
|---|---|
| 開始画面 | 操作の一覧と「はじめる」。押した瞬間から計測が始まり、音も鳴り始める |
| プレイ中 | 10 秒ごとにブラウザ内へ記録を退避する（事故で消えない） |
| ゴール到達 | 自動で終了画面。「記録を保存」で JSON が落ちる |
| 時間切れ | 進行役が **Esc** を押すと終了画面（`cleared: false` で記録される） |

保存し忘れたときは、そのブラウザで開発者コンソールから `__playtest.saveAll()` を実行すると、
その端末に残っている記録がまとめて 1 つの JSON で落ちる（`__playtest.records()` で一覧）。

## 1. 集める人

| 条件 | 人数 |
|---|---|
| キーボードで遊ぶ人 | 3〜4 名 |
| ゲームパッドで遊ぶ人 | 2〜4 名 |
| 合計 | **5〜8 名** |

- 開発に関わっていない人。G0-1 の試遊に参加した人は**含めない**（投影ルールを知っているため）
- 4 世代の実機を触ったことがある人／無い人の両方を入れる（G1-1 の言語化はどちらでも起こるはず）

## 2. 進め方（1 人 25 分）

1. **説明しない**（3 分）
   - 伝えるのは操作だけ：移動・ジャンプ・チャンネル切替（1〜4 / Q・E）・やり直し（R）・ヒント（H）
   - **投影ルール・2D / 3D・世代の特性は一切説明しない**
2. **通しプレイ**（15〜20 分）
   - 詰まっても助言しない。H でヒントが出ることだけは最初に伝える
   - 声に出して考えてもらう（think aloud）。**自発的な発話を書き取る**（G1-1 の判定材料）
3. **終わり**
   - ゴールに着けば自動で終了画面が出る。15〜20 分で着かなければ進行役が **Esc** で終える
   - **終了画面の記入欄で、パズルごとに「何が起きたか自分の言葉で説明できたか」を可否で押す**（T1-28 で追加）。
     押し忘れると未記入になり、集計の分母から外れる
   - 終了画面の「記録を保存」で JSON が落ちる（ファイル名は `playtest_area1_<番号>.json`）
4. **聞き取り**（5 分。§3 の質問文をそのまま読む）

## 3. 聞き取り（言い回しを変えないこと）

| # | 質問 | 見るもの |
|---|---|---|
| Q1 | 面白かった場面を 1 つ挙げてください | 自由回答 |
| Q2 | **CH 1（第1世代）はどんな世代でしたか** | **G1-1**。「粗い」「不便」だけでなく **強み**を自発的に言うか |
| Q3 | 主人公は見やすかったですか。CH 1 のときはどうでしたか | **G1-2** |
| Q4 | 操作でやりにくかったことはありますか | **G1-3** の裏取り |
| Q5 | 一番詰まったのはどこですか。何が分かって解けましたか | ヒント段階の妥当性（T3-04 の入力） |
| Q6 | **部屋ごとに：あそこでは何が起きていましたか** | **所見 2・3 の指標**。答えを聞くのではなく、本人の言葉で言えるかを可否で記録する（T1-28） |

**Q2 で誘導しない。** 「CH 1 の良かったところは？」と聞くと G1-1 の判定が壊れる。
「どんな世代でしたか」まで。回答は原文のまま書き取る。

## 4. 自動で残る記録

```jsonc
{
  "levelId": "area1",
  "tester": "01",                  // ?tester= の値。氏名は入れない
  "startedAt": "2026-08-02T...",
  "device": "keyboard",            // keyboard | gamepad | mixed | unknown
  "elapsedSeconds": 912.4,
  "cleared": true,                 // ゴール到達。Esc で終えた場合は false
  // explained: 進行役の記入。true = 自分の言葉で説明できた / null = 未記入
  "puzzles": [{ "puzzleId": "F-1", "solvedAtSeconds": 74.2, "hintStage": 0, "explained": true }, ...],
  "solvedCount": 6,
  "respawnCount": 11,
  "switchCount": 38
}
```

- `device` は実際に触った入力から決まる（接続されているだけのパッドは数えない）
- `hintStage` は そのパズルで最終的に見たヒントの段階（0 = 使わなかった）
- **入力列そのものは保存しない**（要約のみ）
- 試遊者が `R`（やり直し）を押したら、そこまでの記録を退避して**別の試遊として数え直す**
- 10 秒ごとに localStorage へ退避される。保存し忘れは `__playtest.saveAll()` で回収できる

## 5. 集計とゲート判定

| ゲート | 判定方法 | 失敗時（GAME_PLAN §14） |
|---|---|---|
| G1-1 | Q2 の回答で、**第1世代の強み**を自発的に言語化した人が過半数か | FC 専用パズルを作り直す |
| G1-2 | Q3 で「見にくい」が過半数でないか。魅力について否定的でないか | シルエット・配色を直す。**ドット絵へは戻さない**（§16-2） |
| G1-3 | パズルごとのクリア時間（`solvedAtSeconds` の差分）をキーボード群 / パッド群で比較し、**有意差が無い**か | キーボード側の代替手段を作り直す |

G1-3 は集計ツールが判定する。集めた JSON を渡すだけでよい。

```bash
npm run playtest:report -- playtest_area1_*.json
```

出るもの:

1. 1 人ずつの要約（所要・解けた数・到達・復帰・切替・ヒント段階の合計）
2. パズルごとの所要時間の中央値（キーボード / ゲームパッド）と、その差
3. **G1-3 の合否**（どのパズルでも差が遅い側の 50% 以内なら通過）
4. 併せて見る指標（復帰回数・切替回数・ヒント段階 3 以上に偏るパズル）

所要時間は `solvedAtSeconds` を**解いた順**に差分して出す（解く順は人によって違うため）。
n = 5〜8 では統計的検定に足りないので、実用上の閾値（50%）で判定する。
閾値は `tools/playtest-report.ts` の `DIFFERENCE_THRESHOLD`。判定の計算は
`tests/unit/playtest_report.test.ts` で固定してある。

差が出たパズルは、要求する入力を洗い出すこと
（感圧・アナログの微調整がキーボードで代替できているか）。

併せて見る指標の意味:

- `respawnCount` が突出して多い人がいれば、実行難度が上がりすぎている（§6.6-1 に反する）
- `switchCount` が極端に多ければ、切替の多用による疲弊の兆候（§15、T2-07 の観測対象）
- `hintStage` が 3 以上に偏るパズルは、手掛かりが足りていない
