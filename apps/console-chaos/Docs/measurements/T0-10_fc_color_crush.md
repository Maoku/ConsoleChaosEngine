| 項目 | 値 |

| 日付 | 2026-08-01 |
| 機材 | Apple Silicon Mac（darwin 25.5.0） |
| ブラウザ | 埋め込み Chromium（Claude Code Browser ペイン）、WebGL2 |
| 内部解像度 | 256×224（FC）→ 640×480 へ nearest 拡大 |

| テストシーン | 斜めグラデーション + 虹色の帯 + 動く円 4 つ（`shaders/test_scene_fc.glsl`） |

## 1. 実装した方式（§5.4.6 の候補 B）

2 パス構成。

| パス | 出力解像度 | フラグメントあたりの処理 |
|---|---|---|
| 1. ブロックパレット | 16×14（= ブロック数） | 自ブロックの 256 テクセルを走査 → 54 色へ量子化 → 最頻 3 色の番号を RGB へ詰める |
| 2. 量子化 | 256×224 | 自ブロックの 3 色 + 共通背景色の 4 候補から最も近い色を選ぶ |

## 2. 効果（数値）

画面の 64×64 画素領域に現れた異なる色の数：

| 条件 | 色数 |
|---|---|
| 量子化なし | 39 |
| カラークラッシュあり | **2** |

グラデーションが平坦な帯へ潰れ、円の色がブロック単位で置き換わる
（`t0-10_fc_source_no_quantize.png` / `t0-10_fc_color_crush_16x16.png`）。
これはパズル F-1（色の潰れ）が成立するための前提条件を満たしている。

## 3. 負荷（計測）

シーン描画 → パス列 → 画面 の 1 フレームを 200 回繰り返し、末尾で `readPixels` により
同期して実測。ウォームアップ 20 回。2 回測って平均。

| 条件 | 1 フレームあたり |
|---|---|
| 量子化なし（シーン + blit のみ） | 0.077ms |
| カラークラッシュあり（+2 パス） | 0.768ms |
| **カラークラッシュの増分** | **0.691ms** |

ポストプロセスの予算は 4.0ms（§6.1）。**0.69ms は予算の 17%** であり、
CRT パス（T0-11）と併せても十分に収まる。

## 4. 決定：1 パス方式（候補 A）は不要（§16.1-b / §10-D）

**候補 B（2 パス）を採用し、候補 A は実装しない。**

理由：

1. B の実測が 0.69ms で予算内に収まっており、A を試す動機がない
2. A は「全画素 × 256 テクセル走査」になる。B の第 1 パスが行う走査は
   224 ブロック × 256 テクセルであるのに対し、A は 57,344 画素 × 256 テクセル。
   **同じ走査を 256 倍行う**ことになり、桁が合わない
3. B はブロックの代表色をテクスチャとして持つため、
   デバッグ表示（どのブロックが何色を選んだか）が容易という副次的な利点がある

> IMPLEMENTATION_PLAN §5.4.6 の指示（「A から試して落ちるより、B を実装して
> A の必要性がないことを確認する順で進める」）どおりの結論。

## 5. 所見と次への申し送り

- 量子化の強さ `uAmount` は 0〜1 の連続値。**色覚特性への配慮設定（GAME_PLAN §13）で
  弱められる**が、パズル F-1 の成立条件（色が潰れること）自体は変えない。
  代替手掛かり（形・音）の併設で対応する
- 共通背景色 `uBackgroundIndex` は実機の「背景色」に相当し、
  レベルごとに変えられる。エリアの雰囲気づくりに使える
- 最頻 3 色の選択は「ブロック内の面積が広い色が残る」規則。
  小さく細い形（プレイヤーの武器など）が消えやすいため、
  T0-19（FC 量子化表示の初期確認）でシルエットの読みやすさを併せて見る
- ブロック境界での色の切り替わりは、実機と同様に**縦横 16 画素の格子**として見える。
  レベル要素を 8px グリッドに揃える規則（§5.9 のバリデータ）と整合する

## 6. 再計測が必要になる条件

- 内部解像度を変えたとき
- マスターパレットの色数を変えたとき（走査コストが線形に増える）
- ブロックあたりの色数を 3 から変えたとき
