## 1. 何を作ったか

**外部で描いた絵を 4 セットへ落とす経路**である。上位計画 §2 の事実 10
「外部で描いた絵を入れる経路が無く、入れても現在の検査は通らない」を塞ぐ 1 本の手続き。

`Docs/concept/source/src_*.png`（14 枚）を読み、13 枚を 4 セットへ書き出す。
`src_pedestal_top.png` は取り込まない（実装計画 §2 の判断 J。KV-09 の紋を持たないため）。

| 生成元 | 枚数 | ファイル |
|---|---|---|
| 取り込み（原画あり） | 13 | `grass_top` `stone_floor` `stone_wall` `backdrop_far` `backdrop_near` `tree_pine` `foliage_tuft` `cloud_bank` `water_fall` `gate_glow` `vine_green` `vine_yellow` `enemy_body` |
| 手続き（原画なし） | 4 | `metal_grate` `shell_plate` `mark_glyph` `pedestal_top` |

合計 **17 枚 × 4 セット = 68 枚**（改訂前は 11 × 4 = 44 枚）。
`make-textures.ts` は形の手続きが 11 個から 4 個へ、`SetColors` が 10 群から 4 群へ縮んだ。
**「形の手続き 1 つ・色表 4 つ」という KV-03 の形はそのまま残っている。**

手続きは 3 段しか無い。汎用の画像処理系は作っていない（§11.1.1）。

1. **縮小** … ブロック内の最頻色（判断 B）
2. **セットごとの変換** … 判断 C の 4 行
3. 書き出し

## 2. 縮小は最頻色（平均を使わない）

4×4（滝だけ 2×2）のブロックごとに、最も多く出た RGBA をそのまま採る。

平均を取ると原画に無い中間色が生まれ、**色数の上限（12）と同色連続長（4）の両方を壊す**。
最頻色なら輪郭のアルファも 0 か 255 のまま残るので、半透明の画素が 1 つも生まれない。
票が同数で並んだときは明度の高いほうを採る（順序で結果が揺れないように。不変条件 I4）。

完全に透明な画素は RGB を捨てて 1 つに畳んでから数える。畳まないと、
同じ「透明」が RGB 違いで何票にも割れ、輪郭の外側が不定になる。

## 3. セットごとの変換規則（判断 C）

| セット | 規則 |
|---|---|
| gen4 | 縮小のみ。原画の色をそのまま置く |
| gen2 | 明度を軸に彩度を 1.18 倍し、各チャンネルを RGB555 へ丸める（`v & 0xf8`） |
| gen3 | 同明度の灰青（`[y·0.92, y·0.97, y·1.12]`）と 6:4 で混ぜ、全体を 0.82 倍する |
| gen1 | §4 の宣言写像。**アルファは触らない**（W-3） |

**gen3 の後処理が実際に効いている。** 混ぜた結果が「彩度 40 未満かつ明度 150〜200」の
禁止域（`check-textures.ts` の淡色検査）へ入る色が **7 枚で 7 色**出た。

| 絵 | 混ぜた結果 | 彩度 | 明度 |
|---|---|---|---|
| `grass_top` / `foliage_tuft` / `enemy_body` | `[196,200,207]` | 11 | 199.6 |
| `backdrop_near` / `cloud_bank` | `[177,185,207]` | 30 | 185.1 |
| `gate_glow` | `[185,198,213]` | 28 | 195.8 |
| `water_fall` | `[163,174,197]` | 34 | 173.3 |

このとき**明度を上げて 208 へ抜ける**（下げてはいけない）。
禁止域は「黒と白の間の無彩色」であって、白は禁止ではない（`isMidGray` の上限 200 と同じ根拠）。

## 4. 第1世代の写像（W-4 への答え）

**最近傍では第1世代が作れない。** 14 枚の原画に出てくる主要な色は固定 54 色の 14 個の番号へ散り、
`(148,106,71)`（石畳の目地）、`(219,228,251)`（雲の明部）、`(120,134,170)`（奥の稜線）など
7 色が中間灰へ落ちて形が消える。

したがって写像は**絵ごとの役割**で宣言する（色ごとではない）。
「原画の色を明度順に並べ、その絵に割り当てられた色へ明度順に対応づける」。
表に無い色が来たらその場で落とす（黙って最近傍へ逃がさない）。

| 絵 | 使う色（`FC_PALETTE` の名前） | 上限の根拠 |
|---|---|---|
| `grass_top` | `grass` / `conifer` | 天面は 2 色まで（SG-04 の 16×16 制限） |
| `stone_floor` | `sand` / `sandstone` | |
| `stone_wall` | `sandstone` / `conifer` | |
| `backdrop_far` | `mesa` / `sandstone` / `conifer` | 空 1 + 遠景 3 = 4 番号（第1世代の背景検査） |
| `backdrop_near` | `white` / `skyDay` | |
| `tree_pine` | `conifer` / `grass` | |
| `foliage_tuft` | `grass` / `conifer` | |
| `cloud_bank` | `white` / `skyDay` | |
| `water_fall` | `white` / `skyDay` | |
| `gate_glow` | `white` / `skyDay` / `mesa` | |
| `vine_green` / `vine_yellow` | **同じ 2 色**（`conifer` / `grass`） | F-1 の前提 |
| `enemy_body` | `mesa` / `sandstone` / `sand` | |

ツタ 2 本は第1世代で**バイト単位まで同じ絵**になる（原画の 2 色が同じ明度順に並ぶため）。
F-1 の「第1世代では区別できない」が、色表ではなく写像の結果として出ている。

**ツタだけは 90° 回して取り込む**（`ImportSpec.rope`）。谷に架かる綱として貼るためで、
理由と直しかたは `Docs/measurements/F1_rope_uv.md` にある。

## 6. 計画との差（実装中に判断したこと）

| # | 差 | 理由 |
|---|---|---|
| 1 | `cloud_bank` / `water_fall` も `unlit: true` にした（計画の表では `gate_glow` だけ） | この 3 枚は第1世代で `white` に落ちる。`white` は `lit: false` なので、`unlit` を立てないと「背景専用の色を陰影を受ける絵に置いた」で落ちる。**光そのものを描いた絵に陰影の 5 段を掛ける前提が当てはまらない**のは背景の層と同じ事情である |
| 2 | gen2 の `goal`（`pedestal_top`）を黄色から朱へ移した | 床が砂色（明度 191）になったので、黄色の台座（196）と明度差 3.1 になり下限 20 を割った。R-2 と同じ処方（明度帯で組み直す） |
| 3 | 判断 C の gen3 の実測値が計画の予測と違う（`grass_top ↔ stone_floor` は 59.8 ではなく 24.0） | 計画は `stone_floor` の砂色が禁止域へ入って 208 へ跳ねる前提だったが、実際には彩度 51 で禁止域に入らない。**下限 20 は満たしている**ので処置は要らない |
